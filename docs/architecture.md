# Архитектура

Статус: **черновик на согласование** (Фаза 0).

## Слои

```
 Фронтенд (чужой репозиторий/папка frontend/)
    │  HTTPS /v1/*            │  Realtime (подписка на изменения)
    ▼                         ▼
 API (Go) ──────────►  Supabase: PostgreSQL + Auth + Realtime + RLS
 корзина, голоса,             ▲            ▲              ▲
 jobs (через порты)           │ пишут      │ пишут        │ пишут
                        Воркер цен   Импорт рецептов   Рекомендации
                        prices/      importers/ (+LLM) recommend/
                        └──────────── Python ─────────────┘
```

Языки и связь между частями: [ADR-0006](adr/0006-go-api-python-workers.md).

Фронтенд видит только API, Realtime базы и мок-сервер. Воркер цен и импорт не вызываются
фронтендом: они пишут результат в базу, клиент получает его через API и Realtime.

## Принципы

1. Структурные данные с первого дня: рецепт = список ингредиентов в г/мл/шт на порцию.
2. Всё внешнее заменяемо: магазины (`PriceProvider`), источники рецептов, LLM — за интерфейсами.
3. Цены приблизительные и датированные: магазин, время, источник; устаревшие помечаются.
4. Адрес — часть ключа любого запроса цены.
5. Контракт первичен: OpenAPI до реализации.
6. Минимум нагрузки на чужие сайты: паузы, кэш, robots.txt, проверка условий использования.

## Модули

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `api/` (Go) | Маршруты `/v1`, авторизация, расчёт корзины, пересечение голосов, постановка задач в `jobs` | порты `internal/ports` |
| `prices/` (Python) | `PriceProvider`, провайдеры Дикси/Лента/ручной ввод, подбор товара, воркер по расписанию | порты, БД |
| `importers/` (Python) | Импорт по schema.org/Recipe, разбор строк ингредиентов в г/мл/шт (правила + LLM) | порты, LLM-интерфейс |
| `recommend/` (Python) | Стартовые рецепты, позже «из остатков» и ранжирование | порты, LLM-интерфейс |
| `db/` | Миграции, сиды, реализации портов на Postgres (разработчик БД) | — |

Правило зависимостей: логика не знает про SQL и HTTP, данные получает через порты. Расчёт
корзины (`api/internal/cart`) — чистая функция, покрывается тестами на 100% веток без сети и базы.

## Авторизация и доступ

- Supabase Auth, токен в `Authorization: Bearer`. Способ входа — открытый вопрос (почта / Telegram / Google).
- Пара = `couples` + `couple_members` (2 участника, роль). Все пользовательские таблицы несут
  `couple_id` прямо или через `plan_id`.
- RLS: строка доступна, только если `auth.uid()` состоит в `couple_members` этой пары.
  Справочники (`ingredients`, `stores`, `products`, `prices`) читаются всеми авторизованными,
  пишет только сервисная роль (воркер).
- Воркер и импорт работают под сервисной ролью; ключ только в переменных окружения.

## Асинхронные операции

Тяжёлые операции (`POST /plans/{id}/quote`, `POST /recipes/import`) возвращают `202` и `job_id`.
Статус: `GET /jobs/{id}` (`queued → running → done | failed`). Таблица `jobs` в схеме.
Результат `quote` сохраняется в БД и приходит клиенту также через Realtime.

## Realtime

Фронтенд подписывается на изменения через Supabase Realtime (Postgres changes) по фильтру
`couple_id`. Таблицы и события:

| Таблица | События | Зачем |
|---|---|---|
| `plan_items` | INSERT, UPDATE, DELETE | блюда недели у обоих |
| `cart_lines` | INSERT, UPDATE, DELETE | общая корзина |
| `votes` | INSERT, UPDATE | пожелания партнёра |
| `pantry` | INSERT, UPDATE, DELETE | запасы |
| `jobs` | UPDATE | завершение подбора цен / импорта |

Формат payload — штатный Supabase (`eventType`, `new`, `old`). Конфликты: «последняя запись
побеждает», в строках есть `updated_at` и `updated_by`.

## Расчёт корзины

Чистая функция `build_cart(plan, recipes, pantry, overrides) -> Cart`. Шаги — по плану:
порции → склейка → исключения → запасы → ручные позиции. Подбор товара и упаковки
(`match_products`, `round_to_packs`) отделены: они принимают уже загруженные товары и цены.
Остаток от упаковки сохраняется как «виртуальный запас» и учитывается в следующем плане.
Граничные случаи (весовые товары с шагом 0,1 кг, «только в магазине», нет в наличии,
цена старше 3 дней, неразобранная единица) описываются в `docs/cart-edge-cases.md`
до реализации (Фаза 2).

## Окружения

- local: Docker Compose, локальный Postgres, мок-сервер;
- staging и production: Supabase (Frankfurt);
- секреты только в переменных окружения.

Бюджет инфраструктуры — до 5 €/мес: бесплатный план Supabase, GitHub Actions для воркера цен.

## Что сознательно отложено

КБЖУ (поля в `ingredients` есть, заполнение позже), «что приготовить из остатков»,
оформление заказа и оплата, любой клиентский код.
