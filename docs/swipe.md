# Выбор блюд свайпами

Статус: на согласование. Реализация: `api/internal/swipe`, `suggest.IsMatch`.

Жесты и анимации делает фронтендер. Бэкенд даёт три вещи: колоду, пачку голосов и признак «совпало».

| Жест | Что сохраняется |
|---|---|
| вправо | голос `want` («хочу») |
| влево | голос `dont_want` («не хочу») |
| пропустить | ничего; клиент сам откладывает карточку в конец колоды |

Отмена свайпа: повторный голос за блюдо перезаписывает прежний.

## Колода: `GET /recipes/deck`

В колоду попадают подтверждённые блюда, за которые я ещё не голосовал (любым голосом, включая нейтральный)
и которые не отклонил партнёр: с его «не хочу» блюдо всё равно не попадёт в подборку.

Порядок псевдослучайный, но стабильный для пользователя (хэш пары «пользователь + блюдо»): карточки не прыгают
между запросами, у двоих порядок разный. Курсор хранит позицию в этом порядке, а не номер страницы,
поэтому голосование между запросами его не сбивает. Размер страницы 20, максимум 50.

Умный порядок (разнообразие тегов, вкус по истории) в первой версии не делается; это задача Python-части (`recommend/`).

## Пачка голосов: `PUT /votes`

До 100 голосов за запрос (быстрые свайпы, работа без связи). За одно блюдо в пачке действует последний голос.
В ответе у каждого голоса есть `match`: `true`, если после него блюдо хотят все участники пары.

## Голоса партнёра

Голоса видны обоим участникам пары (решение владельца: ничего не скрываем). Поэтому:

- «Совпало» можно показать сразу из ответа на свайп, отдельных событий не нужно;
- через Realtime по `votes` фронтенд видит свайпы партнёра;
- предупреждение `conflicts` в плане называет, кто против (см. [plan-rules.md](plan-rules.md)).

## Не решено

- Хранить ли «пропустить» на сервере (для разных устройств). Сейчас нет.
- Показывать ли в колоде блюда, которые партнёр уже одобрил, раньше остальных. Сейчас порядок не учитывает чужие голоса.
